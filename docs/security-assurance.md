# Open source security assurance programme

Status: preparation for ISO/IEC 18974:2023 self-certification. No conformance declaration, external ISO certificate or OpenSSF passing badge is asserted. The [programme review](evidence/programme-review.md) records the implemented controls and their evidence. Local candidate results are distinguished from the final hosted release and conformance declaration.

## Scope, accountability and policy

The programme covers Sami Halawa's maintenance and release of `email-smtp-imap-mcp`, its npm distribution, repository, build/test dependencies and runtime transitive components. It does not cover customers' mail servers, MCP clients, local secrets, other projects or an entire legal entity. Release assurance applies to releases prepared from 31 October 2026, beginning with candidate 2.2.1; historical releases are assessed for known vulnerabilities but are not represented as retrospectively archived under this programme. Its objective is to identify, assess, resolve and communicate known vulnerabilities in the supplied software throughout its lifecycle.

Sami Halawa is the sole programme owner, maintainer, security contact, dependency reviewer and release approver. Competence required is TypeScript/Node development, SMTP/IMAP and TLS, dependency/advisory interpretation, regression testing, npm/GitHub release operation and vulnerability communication. The programme review assesses the competence required for these roles against observed repository contributions and operational procedures. Programme objectives, responsibilities and the consequences of bypassing controls are documented there; participant acknowledgement is recorded in the final release review.

Before contributing to security-sensitive work or releasing, each participant reads this policy and SECURITY.md, records their name, role and acknowledgement in the release review, and explains the objectives, their responsibilities and the consequences of bypassing the controls (credential exposure, unsafe releases and inaccurate conformance claims). Sami records assessment and any additional competence action in the same review. Future participants are added by reviewed changes to this section before taking programme responsibilities.

Sami reviews this policy, communication method, assignments, available time/resources and practice alignment at each release, following a serious incident or scope change, and at least annually. Changes and review dates are retained in Git history and the release review. A policy document alone is not evidence that participants received or understood it. Any conformance review must be repeated within 18 months of validation and after material changes.

## Threats, detection and follow-up

The principal threats are plaintext credentials or TLS downgrade, hostile mail content/attachments or oversized protocol responses, untrusted MCP tool arguments, account/sender confusion, vulnerable dependencies, compromised build inputs and secret disclosure through output or logs. Tests cover existing account validation, sender selection, exact IMAP UID access and the TLS regression boundaries. Static analysis supplements these tests; it does not prove the absence of vulnerabilities.

Before every release, Sami checks the exact lockfile and commit with `npm ci`, `npm test`, the CI Semgrep command and `npm audit --json`. GitHub Dependabot configuration supplies post-release dependency alert/update inputs; Sami also checks advisories for all supported release lockfiles before the next release and on receipt of a vulnerability report. Previously released versions remain relevant when determining affected users, even when fixes are provided only in the latest release.

For each finding, use a private GitHub advisory for undisclosed security defects or an issue/PR for already public dependency advisories. Record the advisory/CVE identifiers, affected component/version and release hashes, severity and project exposure, owner, decision, mitigation/fixed version, test and disclosure links. Record a reasoned 'no action' decision when appropriate; never drop a component from the record because an advisory is not exploitable in the present transport. Assess direct and transitive runtime and development dependencies. Missing evidence remains unresolved.

Block release for unresolved critical/high exposure, credential leakage, downgrade or unassessed findings. For lower risks, record rationale, mitigation, owner and follow-up in the release review. If an actual customer agreement exists, record its applicable risk threshold and obtain the required agreement before accepting residual risk; no customer or acceptance is assumed. Recheck the affected component after remediation and identify previously published versions that need an advisory or upgrade notice.

The private reporting route is in SECURITY.md. Sami monitors that route, acknowledges reports with a target of seven days, reproduces and scopes the issue, discusses mitigation/disclosure with the reporter and records the response history. The target is a procedure, not a claim of past response performance. Publish GitHub security advisories and release notes for affected users when warranted, including versions, impact, mitigations and fixes. Share SBOMs, advisory links and non-sensitive risk decisions with third parties on request; protect credentials and unpublished exploit details.

## Components, release evidence and archives

The lockfile records exact npm package versions, dependency relationships, resolved locations and integrity hashes. Each release review must bind the source commit, Node/npm versions, lockfile hash, tests, full audit output, static analysis version/rules/results, npm tarball hash and `npm sbom --sbom-format=spdx` output. The assurance script emits SPDX records with name/version/identifiers/relationships, author and timestamp, alongside a complete lockfile component/origin inventory. The project supplier is Sami; unverified upstream suppliers are explicitly marked `NOASSERTION` as supported by SPDX, with actual archived author/repository metadata kept separately. Review known unknowns and component coverage rather than invent supplier identities. Do not call a dependency count or a lockfile alone a complete component record.

Build and inspect `npm pack` output from that reviewed source; retain the exact distributed tarball, SBOM, review and source snapshot as versioned GitHub release assets. Archive every resolved open source dependency tarball, its integrity and license/source location, including build inputs needed to reproduce the release, in a durable release archive. Public registry availability and an expiring CI artifact are insufficient archives. The archive must permit recovery and integrity verification without relying on the registry remaining online. Test recovery and record it before asserting that the archive requirement is satisfied. The executable `npm run assurance` creates and verifies a local candidate archive. Durable release assets are created only by the reviewed release workflow; local recovery is not proof of remote retention.

CI keeps static analysis results by source SHA for 90 days. Before expiry, release records and results relevant to supplied versions must be moved to the durable release archive. For unsupported past releases with missing archives, record the exact missing versions rather than claim retrospective coverage.

Programme metrics per review: releases with complete component/archive evidence versus total supplied releases; unassessed and unresolved findings by severity; time to acknowledge/fix reports; test/static-analysis coverage and failures; age of policy/competence/awareness/conformance reviews. Targets are complete release evidence, zero unassessed findings at release, zero known critical/high exposed defects at release and reviews within the stated intervals. Actual values must come from retained records.
